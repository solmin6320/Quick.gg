## NH-1. 랭킹 API 학번(로그인 아이디) 마스킹 없이 노출 (round-2)
- **질문**: 기획 의도인지, 마스킹 누락 실수인지?
- **답변**: 학교 내부용이라 학번 노출은 의도된 것. 랭킹에서 누구인지 식별되는 게 오히려 목적에 맞음.
- **후속 질문**: 랭킹 로직은 그대로 두고 보안적으로 추가할 수 있는 방향이 있는지?
- **제안**: RankingService/RankingResponse는 건드리지 않고, `/auth/login`에 실패 횟수 기반 잠금(rate limiting)을 추가 (신규 컴포넌트 `LoginAttemptTracker`, 기존 미사용 `ErrorCode.TOO_MANY_REQUESTS`(429) 활용).
- **사용자 피드백**: 승인. 단, `main`이 아니라 `feature/auth` 브랜치로 전환해서 그 브랜치에서 작업할 것을 요청. 적용 후 변경 내용·흐름·부작용을 확인해달라고 요청.
- **최종 방향**: **적용 완료 (feature/auth 브랜치)**
  - `git checkout feature/auth` 후 `git pull --ff-only origin feature/auth`로 5개 커밋 fast-forward (로그인 기능 관련 커밋들, main과 동일 내용)
  - 신규 파일: `src/main/java/com/example/quick_gg/security/LoginAttemptTracker.java` (학번별 실패 횟수 추적, 5회 실패 시 15분 잠금, 메모리 기반)
  - 수정 파일: `src/main/java/com/example/quick_gg/service/LoginService.java` (로그인 시도 전 잠금 여부 확인 → 실패 시 카운트 증가 → 성공 시 초기화)
  - `./gradlew compileJava` 확인: 기존에 보류하기로 한 `SignupService.java`의 `puuid` 컴파일 에러 1건 외 새로운 에러/경고 없음
  - 영향 범위: `LoginService`의 유일한 호출부는 `AuthController.login()`(`Grep`으로 확인) — 다른 코드에 영향 없음
  - 알려진 한계(사용자에게 고지): 메모리 기반이라 서버 재시작 시 잠금 상태 초기화됨, 다중 서버 인스턴스로 확장 시 인스턴스별로 카운트가 분리됨, 잠금에 도달하지 못한 소수 실패 기록은 자동 만료되지 않고 메모리에 계속 남음(이 프로젝트 규모에서는 실질적 영향 미미로 판단)
  - 커밋은 하지 않음 (작업 트리에만 반영, 사용자가 커밋 여부를 별도로 결정)
